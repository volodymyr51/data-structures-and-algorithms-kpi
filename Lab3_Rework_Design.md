# Lab 3 Rework — Design Proposal

## Обхід матриць: план модернізації (без прив'язки до конкретної ОС, з опційним графічним режимом)

**Статус:** проєктний документ (без коду) — опис архітектури для подальшої реалізації.

---

## 1. Що зберігається, а що змінюється

Оригінальне завдання перевіряє конкретну навичку: реалізувати спосіб обходу двовимірного масиву і показати порядок заповнення візуально, повільно, наживо. Це залишається незмінним. Змінюється лише те, **як** це реалізовано технічно:

| Залишається як є | Змінюється |
|---|---|
| 30 варіантів обходу (спіралі, зигзаги, по рядках/стовпчиках, парні стрілки) | Розділення платформо-залежного коду (`windows.h` / `ncurses`) на один ізольований шар замість дублювання логіки |
| Вимога показувати обхід «наживо», повільно | Спосіб виводу — тепер два змінних рендери замість одного жорстко прив'язаного до консолі |
| Заборона хардкодити проміжні координати та точку зупинки | Алгоритм обходу відокремлюється від виводу повністю — стає чистою функцією без побічних ефектів |
| Автовизначення розміру консолі (розділ 5.4 методички) | Ця функція переноситься в шар рендера, а не розкидана по main() |

## 2. Архітектура: три шари

```
[Параметри варіанта] → [Генератор обходу] → [Послідовність точок] → [Рендер] → [Екран / Вікно]
      (pattern, rows, cols)      (чиста функція,          (масив Point[])   (text або gfx,
                                  без I/O)                                   взаємозамінні)
```

Ключова ідея: **генератор обходу нічого не знає про те, як і куди виводяться точки**. Він просто повертає впорядкований список координат. Це саме та властивість, яку вимагає методичка («не хардкодити», «програма сама обчислює точку зупинки») — тільки доведена до кінця: весь алгоритм стає одним модулем, який можна перевірити окремо від консолі чи вікна.

### 2.1 Модуль `traversal` — генератор обходу (спільний для обох варіантів рендера)

```c
typedef struct { int row, col; } Point;

typedef enum {
    TRAV_ROW_MAJOR_BOUSTRO,   // рядок туди — рядок назад
    TRAV_COL_MAJOR_BOUSTRO,
    TRAV_SPIRAL_CW_IN,        // спіраль за годинниковою, від краю до центру
    TRAV_SPIRAL_CCW_IN,
    TRAV_DIAGONAL_ZIGZAG,
    TRAV_DUAL_ARROW           // два незалежні маршрути, точки чергуються (розділ 5.5.2 методички)
    // ...решта родин, див. розділ 5 нижче
} TraversalPattern;

typedef struct {
    TraversalPattern pattern;
    int start_corner;   // 0=верхній лівий, 1=верхній правий, 2=нижній лівий, 3=нижній правий
    int direction;       // напрямок для спіралей/зигзагів, якщо є вибір
} TraversalConfig;

// Повертає кількість записаних точок (== rows*cols або менше, якщо буфер замалий)
int generate_traversal(TraversalConfig cfg, int rows, int cols,
                        Point *out, int max_points);
```

Функція **не друкує нічого і не має затримок** — це чиста трансформація «параметри → масив точок». Це і є головна відмінність від оригінальної реалізації, де обхід і вивід зазвичай написані в одному вкладеному циклі.

### 2.2 Спільний інтерфейс рендера

```c
typedef struct {
    void (*init)(int rows, int cols);
    void (*draw_point)(Point p, int index, char symbol);
    void (*delay_ms)(int ms);
    void (*cleanup)(void);
} Renderer;
```

`main()` виглядає однаково незалежно від обраного рендера:

```c
Renderer r = use_gfx ? make_gfx_renderer() : make_text_renderer();
r.init(rows, cols);
for (int i = 0; i < count; i++) {
    r.draw_point(points[i], i, '*');
    r.delay_ms(delay);
}
r.cleanup();
```

### 2.3 Рендер №1 — портативний текстовий режим (найближчий до оригіналу)

Замінює `gotoxy`/`windows.h`/`ncurses` на ANSI escape-послідовності, які однаково працюють у Linux, macOS і сучасному Windows Terminal:

- позиціювання курсора: `printf("\033[%d;%dH", row+1, col+1);`
- очищення екрана: `printf("\033[2J\033[H");`
- розмір консолі: одна функція з fallback-ланцюжком — спершу спробувати `ioctl(TIOCGWINSZ)` (POSIX) або `GetConsoleScreenBufferInfo` (Windows) через один `#ifdef`, ізольований в одному файлі (`platform_size.c`), а не розкиданий по всій програмі, як зараз.
- затримка: аналогічно ізольована в один файл (`platform_sleep.c`) — `nanosleep` на POSIX, `Sleep` на Windows, обидва за однаковим сигнатурою `portable_sleep_ms(int ms)`.

Це не повністю усуває платформозалежний код (Windows справді не має POSIX-таймерів), але **звужує його до двох маленьких файлів**, а не дублює всю логіку обходу під кожну ОС.

### 2.4 Рендер №2 — графічний (raylib), опційний

Замість символів у консолі — анімована сітка кольорових квадратів у вікні. Той самий `generate_traversal()`, інший рендер:

```c
void gfx_draw_point(Point p, int index, char symbol) {
    DrawRectangle(p.col * CELL, p.row * CELL, CELL, CELL, FILLED_COLOR);
}
```

raylib обрана тому, що це одна з небагатьох C-бібліотек, які реально ставляться однією командою на Windows/Linux/macOS без складної конфігурації, активно підтримується, і не вимагає розуміння OpenGL напряму — просто `InitWindow`, `DrawRectangle`, `EndDrawing` у циклі.

**Важливо:** це змінює сам формат здачі (з тексту на графіку), тому це — бонусна альтернативна демонстрація, а не заміна текстового рендера за замовчуванням. Раджу здавати текстову версію як основну (вона ближча до формулювання завдання) і показувати графічну як «додатково, якщо цікаво» — варто уточнити у викладача, чи це взагалі прийнятно як заміна.

## 4. Командний рядок замість хардкоду

```
./lab3_text  --variant 17 --rows 9 --cols 9 --delay 80
./lab3_gfx   --variant 17 --rows 9 --cols 9 --delay 80 --cell-size 40
```

Номер варіанта, розмір матриці й швидкість — параметри, а не константи в коді. Це прямо виконує вимогу методички «не хардкодити нічого, крім розмірів масиву», і додатково дозволяє на демонстрації миттєво перемкнутись на будь-який інший варіант за проханням викладача, не перекомпільовуючи програму.

## 5. Класифікація 30 варіантів у «родини» обходу

Зараз кожен з 30 варіантів виглядає як окрема унікальна схема. Насправді більшість — це одна й та сама логіка обходу з різними параметрами (стартовий кут, напрямок, парність рядка/стовпця для «зустрічних» варіантів). Пропоную звести всі 30 до 5–7 родин (`TraversalPattern` вище), кожна з яких реалізована **один раз**, а різниця між варіантами — лише в `TraversalConfig` (стартовий кут, напрямок за/проти годинникової, парний/непарний початок).

Це найбільший виграш у якості коду: замість 30 функцій — одна таблиця `variants.h` на 30 рядків виду:

```c
{ .variant = 17, .cfg = { TRAV_SPIRAL_CW_IN, .start_corner = 0, .direction = +1 } },
```

Щоб зробити цю таблицю коректно, потрібно уважно розкласифікувати всі 30 схем із зображень — я можу зробити це окремим кроком, якщо буде потрібно (у мене вже є всі 30 зображень варіантів з попередньої роботи).

## 6. Збірка

**Текстова версія** (без зовнішніх залежностей):
```
gcc -Wall -std=c11 main.c traversal.c render_text.c platform_sleep.c platform_size.c -o lab3_text
```

**Графічна версія** (потребує встановленого raylib):
```

```

## 7. Ризики та рекомендація

- Текстовий рендер — низький ризик: поведінка та вигляд практично ідентичні оригінальній вимозі, тільки без платформозалежного дублювання коду.
- Графічний рендер — вища якість демонстрації, але змінює формат здачі; варто спершу спитати викладача, чи прийнятна заміна тексту на графіку, чи це має бути лише «бонус на додачу» до текстової версії.
- Рефакторинг у «генератор + рендер» корисний незалежно від того, яку версію здаватимуть — і сам собою підвищує якість коду (тестованість, відсутність дублювання, дотримання правила «не хардкодити»).
